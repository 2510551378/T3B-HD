## 3. `3rd.pkg` 内部结构（核心发现）

### 3.1 组织形式

包是一串 **0x800（2048 字节）对齐**的条目顺序排布，小文件用 0 填充补齐。已确认的条目类型：

| 类型 | 魔数 | 自重长度字段 | 数量 | 合计 |
|---|---|---|---|---|
| 视频 | `PSMF` + `0015` | 头 0x800 + BE32 @0x0C 流长 | **42** | **1,088,458,752 B ≈ 1.04 GiB** |
| 场景实体表 | `SEDBSSCF` v3 | LE32 @0x10 | **245**（对齐命中） | ≈ 53.0 MB |
| 模型/网格容器 | `pack` v2..34 | 头部自述（未展开） | 436 处命中 | — |
| 贴图/UI | `\x89PNG` | PNG 块链 | **12**（头部 0–96 KB） | — |
| 音频 | `RIFF/WAVE` | RIFF 长度 | 624 处命中 | — |

**验证**：42 个 PSMF 的大小首尾相接 41/41 全部吻合（每个视频 `offset + 0x800 + BE32@0x0C`，向上取 0x800 对齐 = 下一个视频起点），说明这个走法是正确的，不是巧合。SEDB 同样 243/244 相接。

### 3.2 空间分布（每 32 MiB 计数）

```
偏移           PNG  PSMF  SEDB  pack  RIFF
0            12     0    91     6   137   ← UI/贴图、脚本、BGM
33 MiB        0     1   153     0   484   ← 脚本 + 音频密集区
67 MiB–1.14 G 0  1~4/窗   0     0     0   ← 几乎全是 PSMF 过场动画
1.14–1.28 G   0     0     0  ~21/窗   0   ← pack 容器（模型/贴图）
1.28–1.34 G   0     0   19~292  47     0   ← 脚本收尾（含 108+292 条）
```

即：**~81% 的体积是 42 段 MPEG-PS/PSMF 过场动画**（本作以长 CG 著称），其次是结尾 200 MB 左右的 `pack` 模型容器，脚本与音频集中在最前面 67 MB。

### 3.3 `3rd.fsd`（7,932 字节）

```
0x00 u32 = 1            版本
0x04 u32 = 0x40         头长 64
0x08 u32 = 0x2f9 (761)  条目数
0x0C u32 = 0x2c  (44)
0x10 u32 = 0x72c (1836) 表偏移
0x14 u32 = 0x1efc (7932) 文件长度
0x18 u32 = 0x50204800    = 3rd.pkg 精确大小（1,344,292,864）
0x1C..0x28              ×3 重复值 0x0d520000
0x2C..0x72C              若干 28 字节记录（含两处接近包尾的偏移量）
0x72C..0x1EFC            762 × 8 字节记录：(u32, u32)，第二字恒为 1
```

- 762 条记录 = (7932−1836)/8，与头部 761 只差 1（末条为哨兵）。
- 记录第一字没有文件名、没有可匹配 `3rd.pkg` 已知文件起点的数值（试过原值 / 与 0xFF 掩码 / 高低半字交换 / 乘 0x800 或 0x1000，均无命中）。
- 可判定的是：**它是给 `3rd.pkg` 用的表**（头部写死了 pkg 精确长度），但不是朴素「偏移+长度」表；编码仍需逆向。
- 实际提取**不依赖它**：各类条目自带长度，能自己走。

## 6. 汉化文本取证：包内没有明文文本

目标：从 `3rd.pkg` 里直接抓中文对白/任务文本。结论是**抓不到，因为不存在明文**。取证如下（全部只读）：

| 测试 | 范围 | 结果 |
|---|---|---|
| GBK / GB18030 / Big5 / Shift-JIS / UTF-8 / UTF-16LE / UTF-16BE 常见字命中 | 245 个 SEDB 全量（53 MB） | 各编码命中数都在随机噪声量级（≈300 次/700 KB），无一处聚集 |
| 单字节 XOR 变形 | SEDB 前 200 KB | 无有效中文 |
| zlib / deflate 流 | 245 个 SEDB | 0 命中（仅偶发 `78 9c` 字节巧合） |
| 全包长 ASCII 串（≥12 字节） | 整个 1.25 GiB | 218,653 种，**没有一条是资源名/标识符**，全是顶点数据产生的 `wwww`、`UUUU`、`ffff` 之类 |
| 0x800 起点魔数普查 | 整个 pkg（65.6 万个块） | 只有 `PNG`、`PSMF`、`SEDBSSCF`、`pack` 四类容器；无 GIM/GMO/TIM2/FTEX 等纹理或字体格式 |
| 12 张包首 PNG | — | 144×80，尺寸太小，不可能是汉字字库 |

**`SEDBSSCF` 到底存什么**（抽取 245 个后实测）：

- 头部：`"SEDBSSCF"` + u32 版本 3 + u32 `0x300400` + u32 文件长度；`+0x18` 起是各段偏移表；`+0x30` 是段内计数。
- 正文：**变长记录表**。例：`sedb_000` 在 `0x4C0` 起是 18 字节一条的记录
  `05 00 | 00 00 | 00 00 | 07 00 | 03 00 | 96 02 | 00 00 | 0c 00 | 00 00`，
  其中夹着 `57 67 bf 3f` / `42 42 02 3f`（float 1.495 / 0.5088）——是**坐标/朝向**。
- 熵值分两类：一类 4.8–6.6（结构化实体表），一类 8.0（压缩流）。
- 结论：**SEDB = 场景实体数据库（Scene Entity DataBase）**，装的是关卡物件摆放，不是台词。

**`pack` 到底存什么**：头部 `"pack"` + u32 类型（2/4/7/8/0x22…）+ 若干 (偏移, 长度) 字段；正文熵 2.97–4.85、未压缩，`0x00`/`0x88`/`0xEE` 占比高 —— 是**网格与调色板贴图数据**，同样不是文本。

所以汉化文本只可能在两处：① 加密的 `EBOOT.BIN`（5.66 MB，`\x7ePSP`）里的编码器/字库；② 某些高熵块里被自有算法压缩的串。两者都需要先有解压器。

## 7. `pack` 容器：原著模型/贴图的所在（阶段一）

读取器：`work/psp_parse/tools/psp_pack.py`（`list` / `show <off>` / `dump <off> <dir>`）。

### 7.1 头部格式（436 个里 435 个通过连续性校验）

```
+0x00  char[4]  "pack"
+0x04  u32      type / version        （实测 2 / 4 / 7 / 8 / 11 / 12 / 34）
+0x08  N × (u32 size, u32 offset)
         N = (首段 offset − 8) / 8，首段 offset 就是头长（头可多 4 字节对齐）
         段与段首尾相接（gap ≤ 0x100），全零的 (0,0) 是空槽
```

校验方法：每段 `offset[i] + size[i]` 应等于 `offset[i+1]`。结果：435/436 容器每段都能接上，段尾恰好落在容器末尾（0x800 对齐）。

### 7.2 清点结果

### 7.3 已破的具体字段

**每个 pack 里最大的 blob 段共用一个描述头**（type 8 的 91 个全部一致）：

```
+0x00 u32 0
+0x04 u32 0x3002      ← 顶点格式字
+0x08 u32 0
+0x0C u16 网格数?     （0x15/0x2a/0x6e/0x45… 逐包变化）
+0x10 u32 0
+0x14 u16 子块数?     （0x10/0x07/0x09…）
+0x18..0x1F 0
+0x20 u32 偏移表（0x36d80, 0xa7a00, 0x1fbf40 …，逐项递增）
```

**`0x3002` 按 PSP GE 的位域拆**：texture=2（16 位 UV）、color=0、normal=0、position=3（**32 位浮点**）、index=3（**32 位索引**）。对比本项目 `FORMAT.md` 的 `0x111E`（UV16+顶点色 8888+顶点 16 位+索引 16 位），是同一套位域。

**贴图表**（type 8，表地址 = blob 段头 `+0x20`）：16 字节一条

```
80 00 40 00 | 04 00 00 00 | 40 26 02 00 | 80 26 02 00
宽128 高64     bpp=4          CLUT 偏移     像素偏移
```
CLUT 紧挨着像素数据：`0x22640` 起是 16 项 × RGBA（`0a0909ff 302b28ff 443e3bff…` 一条灰阶渐变），`0x22640+0x40 = 0x22680` 起是像素，128×64@4bpp = 4096 字节，结束正好 `0x23680` = 下一条记录的 CLUT —— 首尾相接，格式确定。

**FEP 几何块**（`FEP`+版本 4/5）：`+0x08` 头长 0x48、`+0x14` 块大小（与段长完全吻合）、`+0x18..0x24` 若干计数，之后是若干偏移表；块内有浮点材质参数（240.0 / 400.0 / 12.98…）、`0xAA` 填充的打包法线（`0x60000` 区）、`01 0a 0e` 递增的 u8 权重/骨骼流（`0x30000` 区）。

### 7.4 顶点记录已解（导出器可用）

关键手法：`+0x0A` 处的 `0xCCCC` 恒定填充当"尺子"用。t8_a 的几何区里 6,911 个 `cc cc` 间距全部正好 20 字节 —— 顶点记录就是 **20 字节一条**：

```
+0x00  4 × u8    RGBA / 烘焙色（A 基本是 0xFF）
+0x04  3 × s16   位置定点值：米 = raw / 32768 × 3.125
+0x0A  u16       0xCCCC 恒定填充 ← 记录签名
+0x0C  f32       U
+0x10  f32       V
```

证据链：

| 判据 | 结果 |
|---|---|
| `0xCCCC` 间距 | 6,911 个样本全为 20，无例外 |
| UV 取值分布 | 尖峰落在 0 / 0.5 / 1.0 / 1.5 / 2.0 —— 标准网格 UV |
| 位置还原后包围盒 | t8_a：x −1.56..1.69、y −0.39..1.82、z −3.12..0.13 米（1.8 m 级） |
| 长度 | 全部 4,120,816 个顶点的批次数 100% 是 3 的倍数（`3×顶点数 == 3×三角形数`）→ 顶点按三角形拆开，**没有索引缓冲** |
| 导出后三角形质量 | 2,316 面，退化面 0 个，面积中位数 1.2e−2 m² |

所以「索引流」根本不存在：每三个顶点就是一张面。`pack_export.py` 直接按三角形列表写出。

### 7.9 type-12 / FEP 进展

- 每个 FEP 头部 `+0x48` 是对象数（样例 157），随后一张偏移表指向 **12 字节对象记录**：`f32≈3.125`、`u32 0x0001000X`（类型<<16|id）、`u32 数据偏移`（步进 0xC8）。
- 对象数据块里有材质参数（`1.0 / 100.0 / 100.0 / 100.0`）。
- **找到索引缓冲**：FEP 内有四段「全部 u16 < 4096」的区（`0x21000` / `0x2d000` / `0x56000` / `0x83000`），最大值 3593 / 3854 / 3855 —— 这是三段网格的索引。
- **顶点流仍未定位**：FEP 里没有恒定填充字段，`0xCCCC` 尺子在 FEP 上失效（只有 110 个 16 字节间距，不构成长串），20 字节记录假设不成立。
- 附带结论：91 个 type-8 包导出后包围盒全是 2–6 m 的房间，**角色确实不在 type-8 里**。

### 7.10 角色在哪：三路排查都没中
